「利用者として接続する」とは、利用者が認証サービスでサインインし、顧客アプリが、その利用者の資格（アクセストークン）を受け取って、基盤APIを呼ぶことです。基盤は、その利用者の権限の範囲で、操作を許可します。

このページでは、登録済みclient_idとredirect_uriを受け取れる利用環境で、サインインから最初のGET /v1/meが200になるまでを説明します。個別アプリのクライアント登録・BFF接続は準備中、自己登録UI/APIは未提供です。MCPの接続キーは、この方式とは別の資格です。

顧客アプリ・基盤API・認証サービスの違いは、用語集を参照してください。

登場するもの

  • 利用者: サインインする人です。
  • 顧客アプリ: 利用者に代わって、基盤APIを呼びます。
  • 認証サービス: 利用者を確認し、サインインを完了させます。
  • 基盤: アクセストークンを確認し、利用者の権限で、APIを実行します。

全体の流れ

  1. 顧客アプリが、利用者を、認証サービスのサインイン画面へ案内します。
  2. 利用者が、サインインし、MFA（パスワードに加えるもう1つの確認）を完了します。
  3. 認証サービスが、利用者を顧客アプリへ戻し、一時的な「認可コード」を渡します。
  4. 顧客アプリが、認可コードを、アクセストークンに交換します。
  5. 顧客アプリが、アクセストークンを付けて、基盤APIを呼びます。

この方式は、OIDC（OpenID Connect。サインインの標準の方式）の、Authorization Code + PKCEです。PKCEは、認可コードを盗まれても使えないようにする仕組みです。

サインインして、トークンを取得する

  1. Claudia Partnerサポートから、issuer（認証サービスのURL）、client_id（アプリのID）、登録済みのredirect_uri（サインイン後に戻るURL）、scope（求める権限の種類）、基盤のHTTPS originを受け取ります。client_idは、登録済みの値を使います。検証用のredirect_uriが必要なら、利用環境で登録可能な値を確認します。loopbackの利用可否は利用環境によります。
  2. issuerの/.well-known/openid-configurationをHTTPSで読み、返るissuerが、受け取った値と一致することを確認します。authorization_endpointとtoken_endpointを控えます。
  3. 暗号学的な乱数で、stateとcode_verifierを作ります。code_verifierは、43〜128文字の、URLに安全な文字列です。code_challengeは、code_verifierのSHA-256を、base64urlにした値（末尾の=なし）です。code_verifierとstateは、ログに出さず、1回のサインインにだけ使います。
  4. 次の認可URLを、ブラウザーで開き、利用者にサインインとMFAを完了してもらいます。パラメーターは、URLエンコードします。
httpGET <authorization_endpoint>?response_type=code&client_id=<CLIENT_ID>&redirect_uri=<REGISTERED_REDIRECT_URI>&scope=<受け取ったscope>&state=<RANDOM_STATE>&code_challenge=<S256_CHALLENGE>&code_challenge_method=S256
  1. 戻り先（redirect_uri）で受け取ったstateを、保持した値と照合します。一致しない場合や、エラーの場合は、中断します。受け取ったcodeを、1回だけ、トークンに交換します。
httpPOST <token_endpoint> HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Accept: application/json

grant_type=authorization_code&client_id=<CLIENT_ID>&redirect_uri=<REGISTERED_REDIRECT_URI>&code=<CODE>&code_verifier=<VERIFIER>

クライアントは、トークンの交換でクライアントシークレットを使わない、公開クライアント（public client）です。PKCEを使います。scopeは、利用環境で渡された値（通常はopenid）です。アクセストークンに必要な、追加の値は、認証サービスの設定が付けます。トークンを自作して、補うことはできません。offline_accessを、一般の必須のscopeとして、追加しないでください。

応答のaccess_token、token_type、expires_inを使います。リフレッシュトークンが発行されるかは、クライアントの設定によります。IDトークンは、利用者の情報を知るためのもので、基盤APIの呼び出しには使いません。

最初のAPI呼び出し

取得したaccess_tokenを使い、GET /v1/meを呼びます。GET /v1/meは、いま、誰として接続しているかを返すAPIです。

shcurl -sS -H "Authorization: Bearer $CP_ACCESS_TOKEN" -H "Accept: application/json" https://<基盤のHTTPS origin>/v1/me

ヘッダー込みの完全な例は、HTTP・実行例の「利用者を確認」にあります。TLSの検証は、無効にしません。

期待する結果: 200が返り、利用者のid、permissions（権限）、capabilities、セッションの期限が含まれます。permissionsが空でも、確認は成功です。表の操作が許可されている、という意味ではありません。

結果確認すること
401issuer、audience、client、期限、セッション
403現在の権限

署名の検査や認可を無効にして、接続を通さないでください。

サインインの直後とセッションの期限

新しいセッションの方式の稼働版（2026-10以降）では、サインインの直後の反映待ちはありません。サインインが完了したら、すぐにGET /v1/meで確認できます。利用環境の稼働版は、Claudia Partnerサポートに確認します（対応状況とバージョン）。

それより前の稼働版の利用環境では、サインインの直後にGET /v1/meが401（TOKEN_INVALID）になることがあります。その場合に限り、回数と時間を決めて待ってから確認します（例: 0.5秒間隔で、最大20秒）。

新しいセッションの方式では、基盤は、サインインごとにセッションを持ちます。

  • 無操作の時間: 最後の操作から、組織で決めた時間（5分〜720分。初期値は15分）が過ぎると、セッションが切れます。時間は、組織の管理者が管理サイトで決めます。アプリから変える操作は、公開していません。
  • 延長: 成功した操作のたびに、無操作の時間を数え直します。GET /v1/meそのものでは、延長しません。画面を開いているだけでは延長しないので、確認のためだけにGET /v1/meを繰り返しても、セッションは延びません。セッションの残りの期限は、GET /v1/meの応答のsession（idle_expires_at・absolute_expires_at）で確かめられます。
  • 再サインイン: 認証から12時間で、サインインのし直しが必要になります。
  • アクセストークン: アクセストークンの期限は短く（最大5分）、セッションとは別です。期限が切れたら、リフレッシュトークンで取り直します。リフレッシュトークンが発行されていないクライアントは、サインインし直します。

401のcodeで、次の対応を分けます。

code意味対応
TOKEN_EXPIREDアクセストークンの期限切れリフレッシュトークンで取り直す（発行されていなければ、サインインし直す）
SESSION_EXPIRED無操作の時間を過ぎたサインインからやり直す
SESSION_REAUTHENTICATION_REQUIRED認証から12時間を過ぎたサインインからやり直す
SESSION_REVOKEDそのセッションでサインアウトしたサインインからやり直す。続くときはClaudia Partnerサポートに確認
TOKEN_INVALID証明が正しくない、または古い自動で再送せず、時刻・code・request_idを控えて確認

サインインし直すときは、認証サービスで、利用者に改めて認証してもらいます。基盤は、セッションが切れた後、同じサインイン（同じsid）では、認証の時刻（auth_time）が前より新しいトークンだけを受け付けます。ブラウザーに残ったサインインの状態のまま、新しいトークンだけを受け取ると、auth_timeが前と同じため、同じcodeで拒否され続けます。デスクトップのアプリなどで、この状態が続くときは、認可のURLにprompt=loginを付けて、認証し直してもらいます。端末コードの方式（OAuth 2.0 Device Authorization Grant）で、利用者に認証のURLを開いてもらうクライアントは、prompt=loginを付けられません。その場合は、利用者に、ブラウザーのシークレットウィンドウ（プライベートウィンドウ）でURLを開いてもらいます。新しいサインインになるため、拒否は続きません。認証が終わったら、そのウィンドウを閉じてもらいます。

変更の操作は、401のあとに自動で再送しません。サインインし直したあとで、結果を確かめてから操作を決めます。

SESSION_EXPIRED・SESSION_REAUTHENTICATION_REQUIRED・SESSION_REVOKEDは、2026-10-07の固定OpenAPIのcodeの一覧に、まだありません。OpenAPIから作ったクライアントで応答を厳密に検査している場合も、一覧にないcodeを拒否せず、401として扱ってください。

MFAと再認証

人のアクセスでは、MFAと再認証が要るかどうかは、認証サービスの設定で決まります。基盤は、MFAと再認証のために、トークンのacrとauth_timeを判定しません。人のアクセスに、403のMFA_REQUIRED・REAUTH_REQUIREDは返りません。

2つ目の要素

認証サービスでは、パスワードに加えて、2つ目の要素で本人を確かめます。利用者から見える動きは、次のとおりです。

項目動き
方式6桁のコード・端末の認証・キーの3つです。どれを使うかは、管理者が利用者ごとに決めます
端末を覚える2つの要素を通った端末（ブラウザー）では、管理者が決めた日数（0〜180日）のあいだ、2つ目の要素を省きます。パスワードは毎回要ります。0日のときは省きません
共用のPC端末を覚える機能は、共用のPCも区別しません。パスワードを知っている人が、2つ目の要素なしで入れます。共用のPCがあるときは、日数を0にします
キーの方式キーを登録していない人は、パスワードだけでは通りません。登録の画面が出ます
シークレットウィンドウ端末を覚えません。毎回、2つ目の要素が要ります。上の、端末コードの方式で認証し直すときも同じです

トークンの更新と、サインアウト

アクセストークンには、有効期限があります。リフレッシュトークンを発行されたクライアントは、期限が切れる前に、トークンを更新できます。

  • token_endpointに、grant_type=refresh_token、client_id、refresh_tokenを、フォームで送ります。
  • 新しいリフレッシュトークンが返ったときは、安全に保存してから、次の利用へ進みます。
  • 同じ利用者のセッションの更新は、1つずつ行います。古いトークンを、再利用しません。
  • invalid_grantが返ったときは、更新を繰り返さず、再サインインへ戻ります。

サインアウトは、POST /v2/session/logoutで行います（利用者用）。

json{"attempt_id":"<UUID>"}

成功すると、{"status":"revoked","attempt_id":"<同じUUID>","request_id":"<UUID>"}が返ります。結果が不明なときは、同じattempt_idで再送します。このルートでは、Idempotency-Keyヘッダーは要りません。

OpenAPIのツールから使う

公開のOpenAPIの接続先と認証のURLは、接続できない説明用のexample.invalidです。公開ファイルに、実際の接続情報を書き込まず、利用環境版の生成ツールと接続情報の雛形で、手元に利用環境版を作ります。

shpython configure-openapi.py --source openapi.json --profile environment.json --output openapi.environment.json

生成したファイルを、対応するツールに読み込み、PKCEに対応したOIDC認証と、登録済みのclient_id・redirect_uriを設定します。利用環境版には、接続情報が含まれます。公開のリポジトリには、置かないでください。

権限について

管理権限（manage_accessとservice_administrator）と、表の読み取り・書き込み・設計の権限は、別です。表、列、行、期限は、操作のたびに確認されます。利用者を助けるAIも、利用者の権限を超えられません。詳しくは、基盤の考え方と責任分界と、MCPの導入。
